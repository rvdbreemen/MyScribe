{# The transcribe dialog: three ways in, one set of options, one button. Three doors, one at a time: a file, a path, a link. They used to be stacked, each under an "or", which put the submit button below the fold and made every door look equally likely. They are tabs now: all three labels visible so nothing is hidden, one panel open so nothing is in the way. The microphone is not a door here any more. It was the fourth tab, and a person who clicked a microphone found themselves looking at "Upload a file" and "From a link" with no idea why - recording is a different act from handing over something already recorded, so it has a dialog of its own (record_dialog.html) and only the options are shared. The tabs are radio inputs and the switching is CSS (`:has()`), not script, so the dialog works before app.js loads and cannot be left in a state no button can reach. The radio group is named `source_tab` and does reach the server, where every route ignores it: `parse_options` reads only the option fields by name, and the upload, path and url routes each read their own. A test says so, because "the server ignores it" is exactly the kind of thing that stops being true quietly. Options are collapsed. Everything in there has a default that is right for most files, and the summary line spells the current one out, so collapsed does not mean hidden - it means answered. Folder stays outside: filing is a decision about this upload, not a setting. Enter: this form is data-enter-scope, so the key never reaches the browser inside it. The browser would press the first submit in the form - "Add file" - from whichever field the cursor is in. A field opts IN to a button by sitting in a data-submit-row or by naming one with data-enter; everything else swallows the key. Opting in rather than out is the point: the speaker-hint inputs were missed by the first attempt at this precisely because opting out has to be remembered. #} {% import "_macros.html" as m %}
