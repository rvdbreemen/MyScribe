## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Requirements 8 and 9, and Robert's decision of 2026-09-20 (brief: R2). An Ollama that is already there is left alone, in every state. Present with no chat-capable model: one sentence, the copyable `ollama pull qwen3.5:4b`, and a 'Check again'. Never an offer to pull into it. Installed but not running: one sentence and a 'Check again'. It is never started, because people stop Ollama on purpose to free VRAM.

What a user hits today: they keep the preselected 'Ollama, on this machine' (packaging/launcher/myscribe_launcher.py:558) on a machine without Ollama, setup says saved, and the first AI action answers 'Ollama is not running at http://127.0.0.1:11434 (start it, then reload)' (scribe/llm/ollama.py:399). A second program to install, found out after the install is over: the 'separate thing afterwards' Robert asked to be rid of.

The gate has to be MyScribe's own. The design run's readers read Ollama's scripts and reported that install.sh kills and deletes an existing app and that install.ps1 installs unconditionally. Those scripts, the install commands per OS, and the v0.34.2 asset sizes and digests were read from Ollama's README and the GitHub API by a reader agent. Re-verify them before relying on them.

The marker (brief: M1). As first proposed it was written BEFORE the installer ran and never expired. A failed download, followed by the user's own install, later stopped to free VRAM, would then have led MyScribe to run OllamaSetup.exe over an Ollama the user put there - exactly what Robert's sentence forbids. The rules now: it is written only AFTER the installer finished successfully; the installer is never offered again while any Ollama binary exists; it is cleared once Ollama has been seen ready. A failed or cancelled download leaves no marker, and the state is simply 'absent' again. M1 gives the marker's lifecycle and not its purpose. In this record's reading its one job is to let MyScribe finish, after an interruption, the pull it was asked for in the same yes. That is a carve-out from R2's 'never an offer to pull into it', it is not Robert's decision, and criterion 6 states it so that he can overturn it.

The model offer states its unit (brief: W4). Robert's '16 GB' card measures 17,179,344,896 bytes, which is 15.9995 GiB - measured by the critic on 2026-09-20 with torch.cuda.get_device_properties(0).total_memory, and not re-run when this task was written. So 'at least 16 GB' is False in GiB and True in decimal GB on the reference machine. The only measurement in the repository is a code comment: 'the 9B and the 12B both failed to start their runner while 12.7 GB of the 16 GB card was in use' (scribe/llm/ollama.py:221-224). It does not say what held that memory, and it does not give the unit of '12.7 GB'. Read here in the same unit as the card's nominal 16, it left about 3.3 free when the 12B failed. On the same reading a nominal 20 GB card under the same load would have about 7.3 free. That is arithmetic on a figure whose unit is unstated, not a measurement. The weights of gemma4:12b are about 7.6 GB by a reader's figure from Ollama's library in the design run of 2026-09-20, roughly 7.1 GiB if that figure is decimal; it is not in the repository and was not re-verified. An estimated 7.3 free for an estimated 7 of weights, before any context is allocated, is too close to offer automatically. gemma4:12b is therefore never offered automatically on the 16 GB class, and the threshold is set so that it does not flip on the unit one class higher either.

Not included: 'Where should Ollama keep its models?' That is Ollama's own configuration, and it stays an open question for Robert (brief: U7). Until he answers it, a default model folder that is short of space ends the offer with a sentence, not with a way round. llm_num_ctx tuning is left out on purpose as well: it has no writer in Settings, and an install must never be the only place an answer can be given (scribe/setup.py:21-23).

Verified by nobody: whether `OllamaSetup.exe /VERYSILENT` starts the daemon; process lineage under `taskkill /T` after the installer exits; anything on macOS.

Needs a real machine: A machine WITHOUT Ollama, which Robert's is not. Robert: Windows Sandbox or a VM for the installer and the taskkill experiment, and a WSL distribution without Ollama for the guided Linux path. A real Mac without Ollama for the dmg path: Robert, if the Mac of TASK-040.07 (a session on 2026-09-19) is still his to use - not confirmed; otherwise reported as not run. Any path not run is reported as not run.

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 The offer exists only in state absent. Tests with a Popen and a urlopen that raise prove that nothing is run and nothing is downloaded in any other state, 'unknown' included, and that declining writes nothing.
- [ ] #2 Present with no chat-capable model, and no marker: one sentence, the copyable `ollama pull qwen3.5:4b`, and a 'Check again'. There is no offer to pull into it, and a test asserts that POST /api/pull is never called in that state. The one case in which a pull into a present Ollama is offered at all is the marker case of criterion 6, and the two criteria are read together. Installed but not running: one sentence and a 'Check again'. It is never started, and a test asserts that no process is spawned.
- [ ] #3 Before the question is asked, the sitting shows the exact artifact URL, its size and sha256, the command line, where it installs, that no administrator is needed on Windows, and that Ollama updates itself afterwards. A test asserts that the executed command equals the shown command.
- [ ] #4 scribe/ollama_release.json pins the version with a URL, size and sha256 per platform. It lives under scribe/ because packaging/ is not shipped: APP_PATHS carries scribe, pyproject.toml, uv.lock, .env.example and the test clip (packaging/build_payload.py:38). A 404 or a sum mismatch ends as 'get it from ollama.com/download, then Check again', never as an unpinned fallback. The download streams to disk with resume, and nothing large is held in memory. When this file lands, the location question of TASK-089.14 reads its Ollama figures from it instead of the dated literals it carried until then (TASK-089.14 criterion 2).
- [ ] #5 On Windows the sha256 and the Authenticode signer are verified before the pinned installer runs with the shown command line. On macOS the verified dmg is opened and the sitting waits with 'Check again'. On Linux the official commands are shown as download, read, then run - never as a pipe - and the user runs them, then presses 'Check again'. Each command line is re-verified against Ollama's own documentation at implementation, and the notes give the source and the date.
- [ ] #6 The marker is written only after the installer finished successfully. A failed or cancelled download leaves none, and the next sitting sees 'absent'. While any Ollama binary exists the installer is never offered again, marker or not. With the marker standing and that Ollama not ready yet, the sitting may offer to finish the pull of the one model that was shown and agreed to before the install, and nothing else; it still never starts Ollama. After the install's own sitting that offer appears only in a sitting somebody opened with `--setup`, never at a start. This is a choice, stated with its reason so that Robert can overturn it: the user said yes to 'Ollama with this model', and an interrupted pull leaves them with half of what they agreed to. It is this record's reading of M1 and a carve-out from R2, and ADR-015 lists it as an open question. The narrower rule he can choose instead: the pull happens in the install's sitting or not at all, the marker then only explains the state in words, and R2's copyable command applies. The marker is cleared once Ollama has been seen ready, and from then on that Ollama is the user's and is left alone in every state.
- [ ] #7 One test per marker rule, plus the scenario from the critique: a failed download, the user installs Ollama themselves and stops it, the next sitting - no installer offer. And the replaced-Ollama scenario: the marker stands, the user removes the Ollama that MyScribe installed and installs their own, which never gets a chat model. The next sitting offers no pull and shows R2's copyable command, because that Ollama is one the user put there. So if the carve-out of criterion 6 stays, the marker must be bound to what it installed; recording the binary path and the version, and counting only for that one, is the candidate, and ADR-015 lists the question. Under the narrower rule this scenario passes by construction.
- [ ] #8 After the install, GET /api/version is polled for up to 120 s. A timeout reads 'installed, not answering yet', not failure. Whether the installer starts the daemon is verified by nobody, so neither outcome is treated as an error.
- [ ] #9 The model is chosen in the same sitting as the yes, and qwen3.5:4b is the default. The memory comparison is in bytes against the reported total, and the offer says its unit. gemma4:12b is listed only at or above 22 GiB (23,622,320,128 bytes) of CUDA memory. The reasoning behind that number is modelled on one measured card and not on measurements of the others. Robert's nominal 16 GB card reports 17,179,344,896 bytes, a hair under 16 GiB. If 20 GB and 24 GB cards report the same way - just under 20 and 24 GiB; nobody has measured one - then 22 gives the same answer whether it is later read as GiB or as decimal GB: a 24 GB card passes either way, a 16 GB or 20 GB card fails either way, and a threshold of 20 would flip for the 20 GB class on the unit, the way 16 does for Robert's card. On Robert's card it is not listed, and a test pins that number; that is the only measured case. The thresholds are labelled as estimates in the sitting and in the code. On Apple Silicon 12b is not listed at all until somebody has measured it on a real Mac. Tags are always explicit.
- [ ] #10 Free space at Ollama's default model folder is checked before the pull. When it is short, one sentence gives both numbers and nothing is pulled. No way round is offered: where Ollama keeps its models is not MyScribe's to configure (brief: U7).
- [ ] #11 The pull checks every NDJSON line for 'error' and requires a final 'success'. A test with an error line after HTTP 200 reports the pull as failed.
- [ ] #12 After a successful pull, llm_model_ollama=<tag> is written, and llm_provider=ollama is written when no provider row exists: the user said yes to exactly that. The one-word probe and its seconds are printed, under the rule in TASK-089.13.
- [ ] #13 Before anything is promised about Quit, a recorded experiment on a machine without Ollama: install through the setup child, then stop that child both ways - the one process, as Quit is designed to (TASK-089.15 criterion 10), and its tree, the way the launcher stops the app (`taskkill /T /F`, packaging/launcher/myscribe_launcher.py:376-383) - and show for each whether the Ollama processes survive. The same run shows whether the app's own tree kill on a later Quit reaches a daemon the installer started. The notes then confirm or change how the setup child is stopped on Quit, in the light of that result. Until it is run, no sentence in the UI says Quit is clean (brief: M10).
- [ ] #14 While the third-party installer runs, Ctrl-C in the console waits for it to finish, and the Tk window refuses Quit with a sentence saying why.
- [ ] #15 The pin has an owner (brief: M7). docs/RELEASING.md gains a step in its short version: bump the Ollama pin and re-verify it. A CI check confirms that the pinned URL still resolves and that its digest still matches, without downloading the installer on every run; how it reads the digest is in the notes. A probe with a deliberately wrong digest turns it red, and the log is shown.
- [ ] #16 One recorded real run per path on a machine without Ollama. Robert runs the Windows path in Windows Sandbox or a VM, and the guided Linux path in a WSL distribution that has no Ollama. The dmg path needs a real Mac without Ollama. Robert answers it if the Mac that TASK-040.07 records a session on (2026-09-19) is still his to use; that was not confirmed when these tasks were written, and no Mac was available in the design run. If it is not run, the box stays unticked and the parent's final summary lists it. Any path not run is reported as 'not run' and its box stays unticked. Robert's machine proves only the first two criteria.
