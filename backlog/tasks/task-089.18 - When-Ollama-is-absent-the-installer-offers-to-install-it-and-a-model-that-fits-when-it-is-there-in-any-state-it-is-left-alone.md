## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Requirements 8 and 9, and Robert's decision of 2026-09-20 (brief: R2). This task builds under ADR-017 - MyScribe installs third-party software only when it is absent, shown and agreed to, and leaves an Ollama that is there alone - which is decided before this code lands (TASK-089.02 criterion 9; brief: G1). An Ollama that is already there is left alone, in every state. Present with no chat-capable model: one sentence, the copyable `ollama pull qwen3.5:4b`, and a 'Check again'. Never an offer to pull into it. Installed but not running: one sentence and a 'Check again'. It is never started, because people stop Ollama on purpose to free VRAM.

What a user hits today: they keep the preselected 'Ollama, on this machine' (packaging/launcher/myscribe_launcher.py:558) on a machine without Ollama, setup says saved, and the first AI action answers 'Ollama is not running at http://127.0.0.1:11434 (start it, then reload)' (scribe/llm/ollama.py:399). A second program to install, found out after the install is over: the 'separate thing afterwards' Robert asked to be rid of.

The gate has to be MyScribe's own. The design run's readers read Ollama's scripts and reported that install.sh kills and deletes an existing app and that install.ps1 installs unconditionally. Those scripts, the install commands per OS, and the v0.34.2 asset sizes and digests were read from Ollama's README and the GitHub API by a reader agent. Re-verify them before relying on them. Checked again in part on 2026-09-20, against the release data of tag v0.34.2: the release exists, is the latest and is not a prerelease; `OllamaSetup.exe` is 1,569,993,232 bytes and `Ollama.dmg` 197,873,582, with the digests recorded in ADR-017. Not verified: the Windows signer's name, which needs the installer downloaded, and the Linux artifact. Ollama releases often, so this task verifies again at the moment it pins.

The marker (brief: M1). As first proposed it was written BEFORE the installer ran and never expired. A failed download, followed by the user's own install, later stopped to free VRAM, would then have led MyScribe to run OllamaSetup.exe over an Ollama the user put there - exactly what Robert's sentence forbids. The rules now: it is written only AFTER the installer finished successfully; the installer is never offered again while any Ollama binary exists; it is cleared once Ollama has been seen ready. A failed or cancelled download leaves no marker, and the state is simply 'absent' again. M1 gives the marker's lifecycle and not its purpose. Its one job is to let MyScribe finish, after an interruption, the pull it was asked for in the same yes. That is a carve-out from R2's 'never an offer to pull into it', and Robert decided it on 2026-09-20 (brief: G6), against the agent's recommendation of the narrower rule - the pull in the install's own sitting or not at all, and no marker. While the marker stands, a sitting opened with `--setup` offers the unfinished pull again, as a question whose default is No. Finishing an interrupted download with the same button mattered more to him than having no state to keep. For that exception to be safe the marker is bound to the version and the path of what MyScribe installed, and any doubt drops it (brief: G7). It fails to the safe side: after Ollama updates itself the marker lapses, and somebody types one command.

The model offer states its unit (brief: W4). Robert's '16 GB' card measures 17,179,344,896 bytes, which is 15.9995 GiB - measured by the critic on 2026-09-20 with torch.cuda.get_device_properties(0).total_memory, and not re-run when this task was written. So 'at least 16 GB' is False in GiB and True in decimal GB on the reference machine. The only measurement in the repository is a code comment: 'the 9B and the 12B both failed to start their runner while 12.7 GB of the 16 GB card was in use' (scribe/llm/ollama.py:221-224). It does not say what held that memory, and it does not give the unit of '12.7 GB'. Read here in the same unit as the card's nominal 16, it left about 3.3 free when the 12B failed. On the same reading a nominal 20 GB card under the same load would have about 7.3 free. That is arithmetic on a figure whose unit is unstated, not a measurement. The weights of gemma4:12b are about 7.6 GB by a reader's figure from Ollama's library in the design run of 2026-09-20, roughly 7.1 GiB if that figure is decimal; it is not in the repository and was not re-verified. An estimated 7.3 free for an estimated 7 of weights, before any context is allocated, is too close to offer automatically. gemma4:12b is therefore never offered automatically on the 16 GB class, and the threshold is set so that it does not flip on the unit one class higher either.

'Where should Ollama keep its models?' is asked only when the default volume is too small, and never otherwise: decided by Robert on 2026-09-20 (brief: G8, which settles U7). With room, Ollama keeps its own default and there is no question. Without it, a default folder short of space would end the offer with both numbers and no way out, and somebody who put MyScribe on a second drive because the system drive is small would run aground there; Robert's own models were moved to another drive by hand. It engages no existing Ollama, because it happens only for an install MyScribe itself makes in that sitting (criterion 10). llm_num_ctx tuning is left out on purpose: it has no writer in Settings, and an install must never be the only place an answer can be given (scribe/setup.py:21-23).

Verified by nobody: whether `OllamaSetup.exe /VERYSILENT` starts the daemon; process lineage under `taskkill /T` after the installer exits; whether the daemon the silent installer starts inherits an `OLLAMA_MODELS` that was set as a variable of the user's account beforehand (brief: G8); anything on macOS.

Needs a real machine: A machine WITHOUT Ollama, which Robert's is not. Robert: Windows Sandbox or a VM for the installer and the taskkill experiment, and a WSL distribution without Ollama for the guided Linux path. A real Mac without Ollama for the dmg path: the Mac is somebody else's (brief: G9, decided by Robert on 2026-09-20); its points are bundled for the Mac's owner in TASK-089 criterion 10, and until that sitting reported as not run. Any path not run is reported as not run.

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 The offer exists only in state absent. Tests with a Popen and a urlopen that raise prove that nothing is run and nothing is downloaded in any other state, 'unknown' included, and that declining writes nothing.
- [ ] #2 Present with no chat-capable model, and no marker: one sentence, the copyable `ollama pull qwen3.5:4b`, and a 'Check again'. There is no offer to pull into it, and a test asserts that POST /api/pull is never called in that state. The one case in which a pull into a present Ollama is offered at all is the marker case of criterion 6, and the two criteria are read together. Installed but not running: one sentence and a 'Check again'. It is never started, and a test asserts that no process is spawned.
- [ ] #3 Before the question is asked, the sitting shows the exact artifact URL, its size and sha256, the command line, where it installs, that no administrator is needed on Windows, and that Ollama updates itself afterwards. A test asserts that the executed command equals the shown command.
- [ ] #4 scribe/ollama_release.json pins the version with a URL, size and sha256 per platform. It lives under scribe/ because packaging/ is not shipped: APP_PATHS carries scribe, pyproject.toml, uv.lock, .env.example and the test clip (packaging/build_payload.py:38). A 404 or a sum mismatch ends as 'get it from ollama.com/download, then Check again', never as an unpinned fallback. The download streams to disk with resume, and nothing large is held in memory. When this file lands, the location question of TASK-089.14 reads its Ollama figures from it instead of the dated literals it carried until then (TASK-089.14 criterion 2).
- [ ] #5 On Windows the sha256 and the Authenticode signer are verified before the pinned installer runs with the shown command line. On macOS the verified dmg is opened and the sitting waits with 'Check again'. On Linux the official commands are shown as download, read, then run - never as a pipe - and the user runs them, then presses 'Check again'. Each command line is re-verified against Ollama's own documentation at implementation, and the notes give the source and the date.
- [ ] #6 The marker is written only after the installer finished successfully. A failed or cancelled download leaves none, and the next sitting sees 'absent'. While any Ollama binary exists the installer is never offered again, marker or not. With the marker standing and that Ollama not ready yet, the sitting may offer to finish the pull of the one model that was shown and agreed to before the install, and nothing else; it still never starts Ollama. After the install's own sitting that offer appears only in a sitting somebody opened with `--setup`, never at a start, and it is a question whose default is No - never a pull that starts by itself. Decided by Robert on 2026-09-20 (brief: G6), against the agent's recommendation of the narrower rule (the pull in the install's own sitting or not at all, and no marker): finishing an interrupted download with the same button matters more to him than having no state to keep, and a copyable command in a terminal is the separate thing afterwards he asked to avoid (his signed answer in ADR-017's Open Questions). The earlier draft's own argument - that an interrupted pull leaves the user with half of what they said yes to - was the record's, not his. What it costs is accepted with it: the marker is state that can go stale, and R2 carries one exception that has to be explained and tested (criterion 7). One test shows the offer in a `--setup` sitting with its default on No, and one shows that a plain start never makes it. The marker is cleared once Ollama has been seen ready, and from then on that Ollama is the user's and is left alone in every state.
- [ ] #7 One test per marker rule, plus the scenario from the critique: a failed download, the user installs Ollama themselves and stops it, the next sitting - no installer offer. The marker is bound to what it installed: decided by Robert on 2026-09-20 (brief: G7). It records what MyScribe installed, where and when, and it counts only while that same version still stands at that same path. Any doubt drops it, after which the Ollama that is there is left alone and the report gives R2's copyable pull command. One test per lapse case, each asserting that no pull is offered and that POST /api/pull is never called: the version differs, because Ollama updated itself; the path differs; no binary stands at the recorded path; the marker cannot be read or lacks a field. And the replaced-Ollama scenario: the marker stands, the user removes the Ollama that MyScribe installed and installs their own - another version, or another path - which never gets a chat model. The marker lapses, and the next sitting offers no pull and shows R2's copyable command, because that Ollama is one the user put there. What version and path together do not catch is tested too and said in the notes: the same version installed again at the same path gets the one question whose default is No, and nothing happens without a yes. The path alone was not enough: it could not tell MyScribe's Ollama from one the user installed afterwards, because the default path is the same for everybody.
- [ ] #8 After the install, GET /api/version is polled for up to 120 s. A timeout reads 'installed, not answering yet', not failure. Whether the installer starts the daemon is verified by nobody, so neither outcome is treated as an error.
- [ ] #9 The model is chosen in the same sitting as the yes, and qwen3.5:4b is the default. The memory comparison is in bytes against the reported total, and the offer says its unit. gemma4:12b is listed only at or above 22 GiB (23,622,320,128 bytes) of CUDA memory. The reasoning behind that number is modelled on one measured card and not on measurements of the others. Robert's nominal 16 GB card reports 17,179,344,896 bytes, a hair under 16 GiB. If 20 GB and 24 GB cards report the same way - just under 20 and 24 GiB; nobody has measured one - then 22 gives the same answer whether it is later read as GiB or as decimal GB: a 24 GB card passes either way, a 16 GB or 20 GB card fails either way, and a threshold of 20 would flip for the 20 GB class on the unit, the way 16 does for Robert's card. On Robert's card it is not listed, and a test pins that number; that is the only measured case. The thresholds are labelled as estimates in the sitting and in the code. On Apple Silicon 12b is not listed at all until somebody has measured it on a real Mac. Tags are always explicit.
- [ ] #10 Free space where Ollama would keep its models is checked before the offer, and again before any pull. With room at Ollama's default folder nothing is asked, and Ollama keeps its own default. When the default volume is too small, the sitting shows both numbers and asks whether the models should live with MyScribe instead; the default is Yes, because the other answer ends the offer. It is never asked otherwise: decided by Robert on 2026-09-20 (brief: G8, which settles U7). On Windows MyScribe then sets `OLLAMA_MODELS` as a variable of the user's account - the place the app already reads through windows_env (scribe/llm/base.py:194-222) - BEFORE the installer starts, so that the daemon it starts can get it. On macOS and Linux it stays a sentence with the exact command, because a systemd unit wants root and a launch agent is a second mechanism nobody has run. It happens only for an install MyScribe itself makes in that sitting: a test with a writer that raises proves that the variable is never written in any state but absent, and never after a No. Answered No, or short of space at the chosen place as well: one sentence gives both numbers, and nothing is installed or pulled. Whether the daemon inherits the variable is unverified until the run of criterion 13, so nothing in the product says the models went where they were asked to go without checking it first; how it checks is in the notes.
- [ ] #11 The pull checks every NDJSON line for 'error' and requires a final 'success'. A test with an error line after HTTP 200 reports the pull as failed.
- [ ] #12 After a successful pull, llm_model_ollama=<tag> is written, and llm_provider=ollama is written when no provider row exists: the user said yes to exactly that. The one-word probe and its seconds are printed, under the rule in TASK-089.13.
- [ ] #13 Before anything is promised about Quit, a recorded experiment on a machine without Ollama: install through the setup child, then stop that child both ways - the one process, as Quit is designed to (TASK-089.15 criterion 10), and its tree, the way the launcher stops the app (`taskkill /T /F`, packaging/launcher/myscribe_launcher.py:376-383) - and show for each whether the Ollama processes survive. The same run shows whether the app's own tree kill on a later Quit reaches a daemon the installer started. It also measures what criterion 10 leans on (brief: G8): with `OLLAMA_MODELS` set as a variable of the user's account before the installer starts, does the daemon the silent installer starts keep its models there? The output shows the variable and the folder a pulled model landed in. The notes then confirm or change how the setup child is stopped on Quit, in the light of that result. Until it is run, no sentence in the UI says Quit is clean (brief: M10).
- [ ] #14 While the third-party installer runs, Ctrl-C in the console waits for it to finish, and the Tk window refuses Quit with a sentence saying why.
- [ ] #15 The pin has an owner (brief: M7). docs/RELEASING.md gains a step in its short version: bump the Ollama pin and re-verify it. A CI check confirms that the pinned URL still resolves and that its digest still matches, without downloading the installer on every run; how it reads the digest is in the notes. A probe with a deliberately wrong digest turns it red, and the log is shown.
- [ ] #16 One recorded real run per path on a machine without Ollama. Robert runs the Windows path in Windows Sandbox or a VM, and the guided Linux path in a WSL distribution that has no Ollama. The dmg path needs a real Mac without Ollama. The Mac is somebody else's, decided by Robert on 2026-09-20 (brief: G9), so this point is not asked on its own: it goes into the bundled macOS list of TASK-089 criterion 10 with its command and its expected output, and reads 'not run' until that sitting. Robert's machine proves only the first two criteria.
- [ ] #17 A download that fails while a proxy is configured says so in its one sentence, the way the two downloads that existed before this task already do (TASK-089.05 built `credentials.proxy_note()`; the installer's own download and the model pull use the same clause). A test plants a proxy and asserts the clause; without one the sentence is unchanged.
