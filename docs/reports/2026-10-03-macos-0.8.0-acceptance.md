# MyScribe 0.8.0 on macOS: what a walk on this Mac measured

A first-hand acceptance walk of the published `v0.8.0` macOS artifact on an
Apple Silicon Mac, done on 2026-10-03 by an outside tester (not the author, not
CI). Everything below is a command and its output, or a measured number. Where
something was not walked, this says so.

Written because `docs/macos-acceptance.md` opens with "Every point below needs a
real Apple Silicon Mac, and none of them has been run", and because the v0.8.0
release notes repeat that "The macOS app has not yet been walked by a person on
a Mac for this release".

## Environment

| | |
| --- | --- |
| Machine | MacBook Pro, Apple Silicon (`Darwin 25.0.0`, `arm64`) |
| macOS | 26.0, build 25A354 |
| Free disk at the start | 368 GB |
| gh | 2.88.1 |
| Python on `PATH` | 3.13.3 (`/usr/local/bin/python3`) |
| ffmpeg on `PATH` | 9.0.1 (not Homebrew) |
| Ollama | already installed and running, 0.33.1, 11 models |

The Mac had no MyScribe on it before this walk: no `/Applications/MyScribe.app`,
no `~/Library/Application Support/MyScribe`, no `.location` file, no LaunchAgent,
nothing on 4242.

## 1. The download and its provenance (pass)

Both releases published to date were downloaded and checked; `v0.8.0` is the one
installed and tested. `v0.6.0` was checked but not installed, because the walk
moved to the latest release.

```
shasum -a 256 -c SHA256SUMS-0.8.0 --ignore-missing
MyScribe-0.8.0-macos-arm64.dmg: OK
```

The build provenance verifies, and it names the workflow and the commit:

```
gh attestation verify MyScribe-0.8.0-macos-arm64.dmg --repo rvdbreemen/MyScribe --format json
  SAN:         https://github.com/rvdbreemen/MyScribe/.github/workflows/release.yml@refs/tags/v0.8.0
  workflowSHA: 4090de093012c85af1ab6c2bcea44dcc828ce06b   (= the v0.8.0 tag)
  trigger:     push
  subject:     MyScribe-0.8.0-macos-arm64.dmg sha256 4dba274c…40ac
```

Finding (low): `gh attestation verify <file> --repo rvdbreemen/MyScribe` with
its default output prints **nothing at all** and exits 0 on success (gh 2.88.1).
The control run against `--repo cli/cli` prints `Error: no attestations found`.
So the documented command in `docs/installation.md` gives a person no output to
read and no way to tell success from a silent no-op; `--format json` is the only
form that says anything. Worth a sentence in the docs: "no output and exit 0
means it verified".

The bundle itself:

```
shasum -a 256 MyScribe-0.8.0-macos-arm64.dmg
4dba274c92b5409e9da524279a86b486101a4cf3c6a9a11714b18a9ec65240ac
codesign -dv → Signature=adhoc, TeamIdentifier=not set
spctl -a -vvv -t exec /Applications/MyScribe.app → rejected
codesign --verify --deep --strict → valid on disk; satisfies its Designated Requirement
lipo -archs Contents/MacOS/MyScribe → arm64
Contents/Resources/payload/MANIFEST.json → platform macos-arm64, version 0.8.0,
  commit 4090de0…, uv 0.12.13, ffmpeg 8.1.2
```

Finding (low): `CFBundleShortVersionString` is `0.0.0` in the shipped bundle, in
0.8.0 and in 0.6.0 alike, while the app, the window title and `--version` all say
`0.8.0`. Finder's Get Info and System Settings therefore show version 0.0.0 for a
0.8.0 install.

## 2. Install: the app, the first sync, the proof (pass)

The dmg was mounted, the app copied to `/Applications`, and the home kept in a
test folder so nothing landed in `~/Library/Application Support/MyScribe`:

```
cp -R /Volumes/MyScribe-0.8.0/MyScribe.app /Applications/
/Applications/MyScribe.app/Contents/MacOS/MyScribe --home <test home> --headless --sync-only
```

The sync is fast and complete: the environment was built in about 90 seconds
(2,767 MB on disk) with `uv 0.12.13`, CPython 3.12.14, and the bundled ffmpeg and
ffprobe 8.1.2 taken from the app rather than from `PATH`.

The doctor, run through the shipped launcher on that home:

```
[OK  ] python       3.12.14 at <home>/env/bin/python
[OK  ] sqlite       3.53.1, FTS5 available
[OK  ] ffmpeg       ffmpeg version 8.1.2 …
[OK  ] ffprobe      ffprobe version 8.1.2 …
[OK  ] yt-dlp       yt-dlp 2026.8.19 (45 days old)
[OK  ] data-dir     <home>/data writable
[OK  ] disk-space   366.0 GB free at <home>/data
[OK  ] database     schema v17 at <home>/data/myscribe.db
[OK  ] accel        transcription on mlx, diarization on mps
[SKIP] diarization  no local pipeline and no Hugging Face token
[SKIP] models       1.6 GB still to download: whisper-large-v3-turbo …
[OK  ] ollama       Ollama 0.33.1 is running with gemma4:12b, granite4.2:30b, … (11 models)
[OK  ] gpu-runtime  torch 2.10.0 on Apple Silicon: MLX available for transcription, MPS available for diarization
[OK  ] gpu-smoke    large-v3-turbo on mlx/float16: 76 words from 29s in 274.3s (load 22.3s; …)

All required checks passed (skipped: speaker separation not set up; weights not downloaded).
```

An Ollama that is already on the machine is found and left alone, as ADR-017
promises, and the diarization skip explains itself and says where to fix it.

Finding (low, docs): the weights do not land in the home. `whisper-large-v3-turbo`
went to `~/.cache/huggingface/hub/models--mlx-community--whisper-large-v3-turbo`
(1.5 GB) and `<home>/data/models` stayed empty; `scribe/models.py` accepts a
huggingface_hub cache copy as present, so this is by design, but
`docs/installation.md` says "The home holds the speech engine and its caches".
A home chosen on another drive therefore does not hold the weights, and
"your library stays and is yours" leaves 1.5 GB outside it.

Finding (medium, docs): the size on the tin. `Open me first.txt` in the dmg says
"The first start downloads the speech engine (about 1 GB on a Mac)". Measured:
**2.7 GB** for the environment alone (fresh home, after `--sync-only`) plus
1.5 GB of model weights once a transcription runs — about 4.2 GB, before any
media. The window's own line is honest that this was never measured on the
platform ("how much that is has not been measured on this platform").

## 3. /health, the page, and a real transcription (pass)

The app started headless (`--at-login --no-browser`) and answered:

```
GET /health → {"ok":true,"version":"0.8.0",
               "app_dir":"/Applications/MyScribe.app/Contents/Resources/payload/app",
               "data_dir":"<home>/data"}
GET /        → 200, title "All files - MyScribe"
```

A 8.275 s Dutch clip was made with `say` and pushed through the real door:

```
curl -F file=@proef.wav http://127.0.0.1:4242/api/media   → HTTP 201, job 1
```

The job finished `done`:

```
transcribe  model large-v3-turbo  language nl  device mlx  compute_type float16
            n_segments 3  n_words 28  xrt 0.1568
diarize     skipped: weights-unavailable, token_found false
finalize    n_words 28  n_segments 3  n_speakers 0  work_dir_removed true
text        "Dit is een proefopname voor MiScribe. De installatie is gelukt en de
             transcriptie draait lokaal op deze Mac. Aan het eind van deze zin stop
             ik met praten."
```

Wall clock from `queued` to `done`: **52.8 s** for 8.3 s of audio, most of it the
model's first load; the run itself reports `xrt 0.157`. Transcription, jobs,
stages, events, the database and the export data are all real and correct here.

Finding (low, quality): the app's own name comes back as **MiScribe**. The
`correct` stage ran with `n_terms 0` and made no correction, which is right for
an empty glossary — but "MyScribe" is the one proper noun every user of this
program will dictate, announce or say in a note. A one-term default glossary
would be a small, well-evidenced win.

## 5. The first sitting in the window never opens (fail, macOS, blocks a person)

This is the finding that matters, and it is the one
`docs/macos-acceptance.md` point 4 asks for: "the window asks where everything
goes before anything is downloaded; after the sync it shows what it found and
only the open questions".

Three runs, all the same:

1. `open -a /Applications/MyScribe.app --args --home <fresh home>` (a first start
   on an empty home). The window installs the speech engine correctly — the log
   area fills with uv's lines and the home reaches 2,767 MB — and then **stops**.
   The status line stays on "Installing the speech engine. The first start
   downloads the speech engine and its models …". No questions window appears,
   the app never starts, and nothing on 4242 answers. Observed for 10 minutes
   without change.
2. The same home, `--setup` (the Setup button's path, `force_setup=True`): the
   status stays "Preparing…" indefinitely, no questions window.
3. The same home again after a relaunch: identical.

What the machine shows during the hang:

```
osascript … count of windows of process "MyScribe"   → 1        (never 2)
window name                                          → "MyScribe 0.8.0"
pgrep -P <launcher pid>                              → no children
lsof -iTCP:4242 -sTCP:LISTEN                          → nothing
ps -o %cpu,state -p <launcher pid>                    → 0.7 %, state S (idle)
sample <pid> 3 →  2272/2272 samples: Main Thread in _tkinter_tkapp_mainloop → __select
                  2272/2272 samples: one thread in lock_PyThread_acquire_lock
                                     → PyThread_acquire_lock_timed → __psynch_cvwait
```

The main thread is idle in the Tk mainloop; a worker thread is parked forever on
a Python lock. There is no child process, so the sequence is not waiting on the
engine. `run_window`'s `on_tk` schedules the dialog with `root.after(0, run)` and
the worker blocks on `answered.get()`; that answer never arrives, and `run()` is
the only thing that would send it. A windowed PyInstaller build has no stderr, so
whatever happens on that path leaves no trace: `<home>/logs/launcher.log` ends at
the last uv line, and there is no `app.log` at all.

The same home through the console door is fine, which is what isolates the fault
to the Tk dialog path and not to the engine, the sync or the app:

```
echo '{}' | MyScribe --home <same home> --headless --no-browser
The first-run questions were not asked: this is not a terminal and there is no
window. Start MyScribe from a terminal to answer them, or pipe one JSON document
of answers to `python -m scribe.setup --apply-stdin` in the environment MyScribe
installed.
Starting MyScribe...
MyScribe is running at http://127.0.0.1:4242/       → /health answers 200
```

So on this Mac, 0.8.0 cannot be set up, and therefore cannot be used, by a person
who opens the app the way the dmg tells them to. The window does work when there
is nothing to ask: on an already-configured home it prints the log lines and
enables **Open MyScribe**, **Open data folder**, **Setup**, **Quit**, and the app
serves. It is the sitting, not the window, that hangs.

What I could not do: the window is a Tk window with no accessibility children, so
its text cannot be read with System Events, and no Python traceback survives in a
windowed build. The stack above is C-level only. A `threading.excepthook` writing
to `<home>/logs/launcher.log`, even a one-line one, would turn this into a
diagnosis in a single run; that is the cheapest next step for whoever owns
`packaging/launcher/myscribe_launcher.py`.

## 6. What was not walked (and why)

- **Gatekeeper's first-time flow** (`Control-click → Open → Open Anyway`). The
  dmg was fetched with `curl`, which sets no `com.apple.quarantine`, so macOS
  never intervened and the documented prompt never appeared. The app is adhoc
  signed and `spctl` rejects it, so a browser download will still need the
  documented dance; it just was not exercised here.
- **The first-run location question** ("where should MyScribe keep everything"),
  because every run named a home with `--home`, which skips it by design.
- **Speaker separation.** No Hugging Face token was used; the gated pyannote
  conditions were not accepted. The skip is reported correctly and transcription
  is unaffected.
- **Start at login** (macos-acceptance point 6) and the **uninstall** check
  (point 7): not walked. Both need a Settings switch to be flipped in a window
  that this build does not currently open, and point 6 needs a logout.
- **Point 5** (Ollama installed from the dmg MyScribe shows): not walked, because
  Ollama was already on this machine — which `docs/macos-acceptance.md` itself
  says to mark as "Ollama was present".

## 7. Smaller things, in one line each

- `--sync-only` on an up-to-date home prints **0 bytes** and exits 0; when a sync
  is due it prints only uv's own line (`Checked 129 packages in 24ms`), not the
  `tools` / `sync` / `stamp` step lines that `install.py` prints. Neither mode
  writes a `launcher.log`, so a headless or CI run of the shipped app leaves no
  record in the home. The release's own promise — "ends on a proof of what this
  machine measured" — is met by `--doctor` and by `--smoke`, and by nothing else.
- Killing the launcher does not stop the app it started: after `pkill MyScribe`
  the child `python -m scribe --no-browser --port 4242` kept serving until it was
  killed separately. Quit does the right thing; a kill or a crash does not.
- `SHA256SUMS` lists the three `.sha256` files beside the three artifacts, so a
  plain `shasum -c SHA256SUMS` fails on the artifacts that were not downloaded.
  The docs do say `--ignore-missing`, so this only bites someone who skips it.
- `docs/installation.md` still shows `MyScribe-0.7.2-…` in both verification
  examples while 0.8.0 is the latest release.
- Ollama was detected, listed with all 11 of its models, and left untouched. The
  `Ollama address` work in 0.8.0 is invisible from here, which is correct.

## Reproducing the one that matters

```
# fresh home, the way a person does it
open -a /Applications/MyScribe.app --args --home ~/MyScribe-desktop-test
# watch it install ~2.7 GB, then watch it never ask and never start
osascript -e 'tell application "System Events" to count windows of process "MyScribe"'   # 1
pgrep -P $(pgrep -f "MyScribe --home")                                                  # nothing
curl -s http://127.0.0.1:4242/health                                                    # refused
```

## Appendix B: how this was produced

- Everything was driven from `bash` on the Mac itself; no CI, no other machine.
- Commands and their full output are in the evidence folder, one file per step, named in
  the order they were run.
- The launcher's windows were read with `screencapture` plus a local vision model
  (Ollama `qwen3-vl:8b` on the same Mac), because a Tk window exposes no
  accessibility children: `System Events` reports one window with a title and
  nothing inside it. Where the report quotes a window's text, that is how it was
  read.
- The two hangs were characterised with `sample <pid>`, which is where the C-level
  stack in section 5 comes from; `sample` shows no Python frames, and a windowed
  PyInstaller build has no stderr, so no Python-level traceback exists to read.
- The source was read at the `v0.8.0` tag from a clean clone
  (`v0.8.0-2-g7676282`, working tree clean) — the launcher and the engine
  behaviour were cross-checked against the code that shipped, not against `main`.
- Nothing was pushed and no fork was made: the tester's GitHub account has read
  access only to this repository.
